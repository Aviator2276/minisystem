# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

MiniSystem is a full field-management system (FMS) for MiniFRC robotics events — a web rewrite of the Electron app `Custom-MiniFRC-FMS`. It covers auth (admin + team accounts), event/team management, qualification scheduling, server-driven match control, judge scoring, a live display screen, alliance selection, double-elimination playoffs, team dashboards, and public/TV pages. The original 17-phase build plan lives at `reference/minisystembuildplan.md`; all phases are implemented.

## Commands

The repo uses **npm** (only `package-lock.json` is present, despite `.cta.json` mentioning pnpm).

- `npm run dev` — dev server on port 3000 (includes WS upgrade via a Vite plugin)
- `npm run build` — two Vite builds: the app, then the server/WS bundle (`vite.ws.config.ts`)
- `npm start` — production server (`server/index.mjs`: srvx + static files + crossws upgrade; runs `bootstrap()` for migrations + admin seed)
- `npm test` — Vitest once; `npx vitest <pattern>` / `npx vitest watch` for one test / watch
- `npm run typecheck` / `npm run lint` / `npm run format` / `npm run check`
- `npm run db:generate` — drizzle-kit migration from schema changes; `db:migrate`, `db:seed` (admin user)

Env vars: `DATABASE_PATH` (SQLite file), `ADMIN_USERNAME`/`ADMIN_PASSWORD` (boot seed/reset), `MINISYSTEM_DISABLE_DEVTOOLS=1` (see Gotchas).

## Architecture

- **TanStack Start** (React 19, srvx/h3 — no Nitro) with file-based routing. `src/routeTree.gen.ts` is auto-generated — never edit. Route groups: `admin/` (control panel, event/team CRUD), `judge/$eventSlug` (phone scorer), `display/$eventSlug` (arena screen), `public/$eventSlug` (+ `/tv`), `team/` (team dashboard), `login/` (default `/login` is the **team** sign-in — a 2-digit OTP for the zero-padded team number + password; `/login/admin` is the admin email/username form). All auth redirects point at `/login`, which routes by returned role. Events are addressed by name-derived **slug**.
- **All mutations are HTTP server functions** (`src/server/functions/*`) built as `createServerFn().middleware([requireUser/requireAdmin]).validator(zodSchema)`, thin wrappers over `src/server/services/*`. (Use `.validator()`, not the deprecated `.inputValidator()`.) Functions that change shared state `publish()` to WebSocket topics.
- **Realtime**: crossws on `/_ws`, topics `event:{id}:{display|control|judge|public}` (`src/shared/realtime-messages.ts`). Clients receive via `useRealtime()` and write only through server functions — never through the socket. Dev WS is wired in `vite.config.ts`; prod in `server/index.mjs`. `useRealtimeStatus()` exposes the live socket state (`connecting|open|closed`) + a manual `reconnect()` — used by the judge screen's "out of sync" notch. Note the two judge channels are independent: scoring + presence heartbeats are HTTP (work even with a dead socket), the WebSocket only pushes live updates, so "out of sync" ≠ "can't submit".
- **DB**: Drizzle + better-sqlite3 (`src/db/schema.ts`). Scoring is event-sourced: `score_events` is the source of truth, with cached aggregates on `matches`; rankings are computed on demand. Alliance selection is an append-only `selection_actions` log reduced by the pure state machine in `src/server/selection/state-machine.ts`. The reducer replays the log against the *live* ranking order, so once selection is locked in (`status` ≥ `playoffs`) `getSelectionState` reads the materialized `alliances` + `event_teams.selectionStatus` instead of replaying — a later qual-score edit can shift rankings and make a recorded invite land on a now-locked captain. Event children cascade on event delete.
- **MatchEngine** (`src/server/engine/`): server-authoritative match timer driven by the game's `timeline` (setTimeout chains); recoverable from DB after restart; held in `globalThis` singletons (`getSingleton`, `src/server/engine/registry.ts`) so Vite reloads don't duplicate it. Timer sync uses absolute `phaseEndsAt` deadlines plus `useServerClock()` (ping/pong offset median) on clients. Server-side state (engine, game defs) does **not** hot-reload — restart the dev server to pick up changes there.
- **JudgeRegistry** (`src/server/judges/`): in-memory presence + per-match submission tracking for judge scorers, same singleton/`publish` pattern as the engine. A judge becomes active on alliance pick and stays active while it heartbeats (pruned after a TTL); `judgeSubmit` flags it done for a match without posting. Broadcasts `judges_update` to the control channel only on change; the control panel's Publish block gates "Publish results" on the submitted count (with override).
- **Playoffs** (`src/server/playoffs/`): hand-built double-elim templates for 2–8 alliances (every count is true double-elim — `2N-2` matches, single grand final, no bracket reset; even 2 alliances play two matches); `resolveBracket` fills `winner:`/`loser:` sources idempotently. The **grand final swaps alliance colors** vs the rest of the bracket — the lower-bracket finalist is `red`, the upper-bracket finalist `blue` (baked into each template's `F` slot). Playoff ties are rejected at score posting. Alliance count is capped at `MAX_PLAYOFF_ALLIANCES` (8, in `selection/state-machine.ts`): `allianceCountFor` is `min(8, floor(teams/3))`, and `generateBracket`/`getBracket` clamp to the top 8 seeds so an event with 9+ already-formed alliances still brackets (surplus alliances sit out). Bump that one constant + add templates to support more.
- **Best-of-3 finals** (`events.settings.finalsBestOf3`, toggled in the control panel's Control card): `expandFinalsBestOf3` (in `templates.ts`) replaces the single `F` slot with a **F1/F2/F3 series between the same two finalists** — all three games share the same `winner:M…` feeder sources because the same two alliances replay every game (that is *not* a bug). **Game 2 swaps red/blue** (`red`/`blue` sources flipped) to even any field bias. `getBracket`'s champion is whoever wins the **majority** of the finals (`floor(n/2)+1` — so 2 of 3, or 1 of 1), meaning a 2-0 lead crowns the champion *before* game 3 is played (an extra game can't change the result, so it's never blocked). **Bracket layout gotcha**: the base template only has an `F` slot, so `getBracket` must compute the `bracket`/`round` metadata for `F1`/`F2`/`F3` itself (`slotMeta` → `bracket: "final"`, `round: finalRound + gameIndex`); without this they default to `round 1`/`upper` and all stack in the leftmost column. With it they render as a **left-to-right row** in the final lane. `BracketGraphic` draws F1's normal feeder lines but **chains F1 → F2 → F3** (instead of feeder lines *into* F2/F3) so the series reads as a row in succession. Match labels read **Final / Final 1·2·3** for `F`/`F1`/`F2`/`F3` (`matchShortLabel`/`matchLongLabel` take an optional `bracketSlot`). Toggling `setFinalsBestOf3` (`functions/playoffs.ts`) regenerates an existing un-posted bracket immediately and is rejected once a playoff match has posted; the setting rides `settings_update` (now carrying an optional `finalsBestOf3`).
- **Backup robots** (display/roster only): an alliance can gain a 4th team via `alliances.backupTeamId`, set during *playoffs* from the control panel (`setSelectionBackup` → `setAllianceBackup` service — validates the team isn't already rostered, then re-runs `resolveBracket`). `resolveBracket` denormalizes it into `matches.red4`/`blue4` for unposted matches (the same pattern as captain/picks → red1/2/3), and `EnrichedSelectionState` alliances carry a `backup`. It does **not** affect scoring — the judge pad stays 3 robots and red-card zeroing keys off `red1/2/3` only. Roster render sites show the 4th team (tagged "BACKUP") *only when assigned*; quals/backup-less matches stay 3-wide.
- **Cards / disqualification** (`src/server/services/cards.ts`, pure math in `src/shared/cards.ts`): per-event `cards` rows (yellow/red, with a reason), stored individually; `computeCardStates` reduces them to per-team `{yellows, reds, effectiveReds, disqualified}`. Escalation is pure (`effectiveReds = reds + floor(yellows/2)`, DQ at `DQ_THRESHOLD` 2 — so 2 reds, 2 yellows + 1 red, or 4 yellows) with a colocated test; **yellows still render as individual yellow cards** (they don't visually collapse into a red). `issueCard`/`revokeCard` (admin) broadcast a `toast` + a `cards_update` message; views carry per-team card state on `getDisplayBootstrap().teams[].cards` and re-fetch on `cards_update`. **Red-card score zeroing (FRC-style)**: a red card to a team in the *live* match (`event.currentMatchId`, status running/scored) links `cards.matchId`; `recomputeMatchScore` derives the carded alliance from non-revoked red cards (keyed off `red1/2/3`/`blue1/2/3`) and zeroes that alliance's cached totals — flowing into `postMatch` winner/RP and the live scoreboard. Revoking recomputes. **DQ effect**: `rankedTeams` (selection) filters out disqualified teams, so they can't be a captain or be picked (blocked from playoffs); `TeamCards` renders the overlapping-card graphic next to team numbers on the display scoreboard + public tabs, and DQ'd teams are struck-through/dimmed there.
- **Audience display & TV** (`src/routes/display/$eventSlug`, `src/routes/public/$eventSlug/tv`): the arena screen renders one of `DISPLAY_VIEWS` (`src/server/functions/display.ts`), admin-picked from the control panel's `VIEW_GROUPS` ("Match play" / "Informational" / quick views), persisted on `events.displayView` and broadcast as `view_change`. The TV instead **auto-rotates** its own `PanelId` list. Both pull `getDisplayBootstrap` (public, rate-limited) and live-update over the `public` channel: views read local state patched by `score_update`/`match_state`, and **invalidate the loader on `bracket_update`/`settings_update`/`cards_update`**. Newly generated playoff matches reach the screen *only* via that refetch — `display/$eventSlug` re-seeds its `matches` state from `boot.matches` (the loader keeps a stable reference between fetches, so this never clobbers the live `score_update` patches). Shared, surface-agnostic view components: `BracketGraphic` (highlights the **current** match — pulsing green ring + "Current" notch — and the **next** — steady yellow + "Upcoming"; computes "next" itself from `currentMatchId`; draws an SVG overlay of **one emerald line per match → where its winner advances**, derived from each row's `winner:SLOT` source — loser drops are intentionally not drawn. Two subtleties: lines are measured in **layout space** via an `offsetWithin`/offsetParent walk, *not* `getBoundingClientRect`, so they stay aligned under `ScaleToFit`'s CSS transform; and match cards must stay **opaque** — dark mode uses an opaque `color-mix(white 5%, var(--background))` instead of a translucent `bg-white/5`, or the behind-the-cards lines bleed through. Each line exits the card's right edge and routes in a per-destination-column vertical channel so they don't overlap), `ScaleToFit` (measures natural vs container size and uniformly scales the bracket to fill any screen), `ScheduleView` (rolling 5-match window: prev / current / next×3, same green/yellow highlight language, Motion `layout` animations), `SelectionBoard`, `Scoreboard`. The bracket/notch pulse is the `bracket-pulse` keyframe in `src/styles.css` (animates an **inset** ring so it's never clipped by the lane's `overflow-x-auto`).
- **Control-panel layout** (`control.tsx`): the top **Control** card is two columns — left stacks **Field entry** + **Match control**, right is a **Settings** column of `SettingSwitch` toggles (**Blue on left** → `flipAllianceSides`, **Advance on lineup**, **Finals best of 3** → `finalsBestOf3`). These toggles live in `ControlPanel` (state + handlers) so the `DisplayCard` below only handles view switching; `advanceOnLineup` is passed into it as a prop.
- **Control-panel display conveniences** (`control.tsx` `DisplayCard`): switching the audience view can apply side effects. Moving to **camera** after a match ended (`field.phase === "post_match"`) auto-sets field entry to *safe to enter*. The **"Advance on lineup"** toggle makes showing the **lineup** queue the next still-scheduled match after the current one (`setCurrentMatch`), so the lineup is always the upcoming match. `nextMatchId` anchors on `field.matchId` and is `null` when nothing is queued — it never falls back to the first match in the schedule. The **lineup and results views show each alliance's number** (animated badge, alliance-color tokens) during playoffs — derived in `display/$eventSlug` by looking the current match up in `boot.bracket.matches` (`null` for quals/practice, which have no alliances). The results view also shows each alliance's team numbers + names and celebrates an **event-specific** single-alliance high score (golden highlight + confetti for the record-setting alliance, computed from every *other* posted match's `redPoints`/`bluePoints`).
- **Game plugin** (`src/games/stronghold/`): two distinct concepts — `phases` is the **scoring taxonomy** (auto/teleop/endgame) the judge UI groups buttons by and `scoreEventTypes` reference; `timeline` is the **engine clock** (segments with entry `sound`s plus mid-segment `cues`) the MatchEngine and display countdown run on. They diverge on purpose (e.g. Stronghold's endgame is one continuous `teleop` segment with the warning delivered as a cue, so the display timer never resets). Plus score event types and pure reduce/computeTotals/computeRP — add new games here, keep scoring pure.
- **Docker**: single-container deployment (`Dockerfile`, node:22-slim multi-stage); `bootstrap()` (`src/server/bootstrap.ts`) migrates and creates/resets the admin account from env on every boot.

## Conventions

- **Tailwind CSS v4** via Vite plugin + `src/styles.css` (no `tailwind.config`); compose classes with `cn()` from `src/lib/utils.ts`. Alliance colors come from the `--alliance-red`/`--alliance-blue` tokens in `src/styles.css`.
- **Alliance side ↔ color**: never hard-code `["red", "blue"]` or assume red-is-left when an alliance color depends on a left/right (or top/bottom) position. Derive the order from `allianceOrder(event.settings.flipAllianceSides)` in `@/shared/alliance` (e.g. `const [leftSide, rightSide] = allianceOrder(flip)`), then color each slot from that side's `--alliance-{side}` token. `flipAllianceSides` is toggled in the control panel and broadcast as a `settings_update` realtime message, so anything reading it must invalidate/update on that message.
- **No rounded corners** — the theme sets `--radius: 0` (all `rounded-*` utilities resolve to square, so shadcn's `rounded-md`/etc. are already correct). Don't add corner-rounding; keep edges sharp. Even `rounded-full` is avoided in app code (page-indicator dots etc. are square); the only `rounded-full` left is in generated `src/components/ui/*`.
- **Match ordering** — display matches grouped by type via `sortMatchesByType` (`@/shared/match-format`): **practice → qualification → playoff**, then play order (`scheduledOrder`). Used by the admin matches table and the control-panel match queue. `scheduledOrder` is the persisted play order (drag-to-reorder on the matches table writes it).
- **shadcn/ui** (`components.json`: style `radix-lyra`, base color `mist`, lucide icons) in `src/components/ui/` — treat as generated (eslint/prettier-ignored); add via `npx shadcn@latest add <name>`. Always prefer shadcn components (Dialog/AlertDialog/Select/Tabs) over natives or custom CSS.
- **Animations** use Motion (`motion/react`), concentrated on the display screen (`src/routes/display/$eventSlug.tsx`).
- **Path alias** `@/*` → `src/*`. TypeScript is strict with `noUnusedLocals`/`noUnusedParameters` and `verbatimModuleSyntax` (use `import type`).
- Pure logic (engine, selection, playoffs, scoring, matchmaker) has colocated `*.test.ts` Vitest suites — extend them when changing that logic.

## Gotchas

- **`@tanstack/devtools-vite` strips the `<TanStackDevtools>` JSX element during production builds.** The element must sit directly inside enclosing JSX — wrapping it in `{condition && ...}` leaves invalid syntax after removal and breaks the build. Keep the `src/components/app-devtools.tsx` indirection (early-return condition, element in a fragment).
- **Never render clock/countdown values during SSR** — they cause hydration mismatches that silently break WebSocket updates. Gate on a `mounted` flag.
- For headless/automated runs (e.g. Playwright), start dev with `MINISYSTEM_DISABLE_DEVTOOLS=1` and a scratch `DATABASE_PATH` — the devtools console pipe otherwise enters an SSE error loop that floods logs and blocks clicks.
- **recharts pulls in `es-toolkit/compat/*`, whose subpath exports are CJS-only** (no `import` condition). In the minified production build Rollup's CJS→ESM interop mangles a nested require into `var r = r()` → **"r is not a function"**, crashing any page that uses a chart (the team dashboard radar/points charts) — dev is fine because esbuild pre-bundles it. The `esToolkitCompatEsm` plugin in `vite.config.ts` (build-only) redirects those flat default imports to the ESM barrel `es-toolkit/compat`. Keep it; it's why charts don't break in prod.
- **Preload audience-display sounds.** A fresh `new Audio(src).play()` per cue fetches+decodes first, which lagged the results sound. `display/$eventSlug` caches one `Audio` per cue (preloaded once `armed`) and `playSound` just rewinds + replays it. Audio only unlocks after the user's *arm* gesture; preview mode stays silent.
- **Playoff matches resolve their teams lazily** — `resolveBracket` fills `red1/2/3`/`red4` (and `blue*`) only as feeder matches post. A client holding a loader snapshot can therefore render a queued match with stale/empty slots; on the judge scorer that surfaced as a single robot (`robotsFor` floors the count at 1). Any client showing a queued match's roster must refetch on `field.matchId` change (the judge page calls `listMatches` in an effect) rather than trust the initial load. Quals don't hit this — their teams are set at schedule generation.
